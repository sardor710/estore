## 1. Requirement

### Owner's request (2026-11-17)
"Build user account page where he can change its own details and see orders, shipping address and much more. Normal user UI profile." Sign-in: **B — through the shop's Telegram bot** (owner's pick). Feature set: owner said "your choice" → everything below marked *(my call)*.

### What exists today (recon)
- Storefront `src/app/[locale]/*` (uz default, ru, en; next-intl). **No customer login**: checkout (`CheckoutForm.tsx`) asks name, phone (normalized by `normalizeUzPhone`), region, address, comment on every order; cart in `localStorage`, prices re-quoted from DB.
- `Order` has `phone`, `name`, `region`, `address`, `locale`; `Customer` = one row per normalized phone (admin Clients, `blocked` flag), auto-created on each order.
- Public order page `/{locale}/order/{number}` shows only number + status (by design).
- Telegram: `src/lib/telegram.ts` sends staff order alerts with bot token + chat id from Settings; the bot receives nothing today.
- Staff auth: jose JWT cookie `admin_session` (`src/lib/auth.ts`, `SESSION_SECRET`), separate from what we build.

### Decisions
| Topic | Decision |
|---|---|
| Sign-in method | **Telegram bot** (owner). No SMS, email or passwords. |
| First sign-in *(my call)* | Site → "Sign in with Telegram" opens `t.me/<bot>?start=login_<token>` (QR code on desktop). Bot asks the user to **share their phone contact** (Telegram's own button; accepted only if the contact is the sender's own). Bot asks the user to **pick, from 3 buttons, the 4-digit code shown on their website screen** (revised after threat model; wrong pick cancels) and then sends a "New sign-in — not you?" message. The website page polls and signs in. Token: random, single-use, 10 min, bound to the starting browser by an httpOnly cookie (another browser can't collect it). |
| Later sign-ins *(my call)* | Same button (bot already knows the phone → only the confirm step), **or** enter phone on the site → bot sends a 6-digit code to the linked chat → enter it. Code: 5 min, 5 attempts, rate-limited per phone and IP. A phone never linked gets "use the Telegram button first". |
| Phone rule *(my call)* | Account phone must pass `normalizeUzPhone` (the shop sells in Uzbekistan); other numbers get a clear localized message. |
| Bot transport *(my call)* | Production: webhook `POST /api/telegram/webhook` with Telegram `secret_token` header check; a "Connect bot" action in admin Settings (full admin) registers it at `SITE_URL`. Local dev: `npm run bot:poll` (long polling). Same bot as staff alerts; bot username read via `getMe` and cached. |
| Data *(my call)* | Account lives on the existing **Customer** row (phone unique): add Telegram user/chat id, preferred locale, notification on/off, session version, account created/deleted timestamps. New tables: login requests/codes, **CustomerAddress** (label, recipient name, region, address, default), **Favorite** (customer, product). Additive migration. |
| Session *(my call)* | Separate httpOnly cookie `customer_session` (jose JWT, distinct audience from staff, 30 days, SameSite=Lax), revocable via session version ("sign out everywhere", account deletion). Staff and customer sessions never mix. |
| Account pages *(my call)* | `/{locale}/account` overview (greeting, last order, default address, quick links); `/account/orders` list with status badges; `/account/orders/{number}` detail (items with photos, variant names, prices, discount, total, address, status timeline from the order's status history, **Buy again**); `/account/addresses` (add/edit/delete, set default, max 10); `/account/favorites`; `/account/profile` (name, language, Telegram notifications on/off, sign out, sign out everywhere, **delete account**). `/{locale}/login`. All noindex, uz/ru/en, mobile-first, same look as the storefront. |
| Orders shown *(my call)* | All orders whose phone equals the account phone, including ones placed before the account existed. Another customer's order number → 404. |
| Checkout *(my call)* | Signed-in: name prefilled, **phone fixed to the account phone** (so the order shows in the account), address picker from saved addresses (default preselected) + "Save this address" checkbox. Guest checkout unchanged. Blocked customers can sign in and see history but still can't order (existing rule). |
| Buy again *(my call)* | Adds the order's still-available variants (current price, capped by stock) to the cart and opens it; unavailable lines listed as "no longer available". |
| Favorites *(my call)* | Heart on product cards and product page; signed-out tap → sign-in prompt (no guest favorites). |
| Status notifications *(my call)* | When staff change an order's status, the bot messages the customer (order's locale, link to the order page) if the phone has a linked account with notifications on. Failures never block the status change. |
| Header *(my call)* | Account icon in the navbar: "Sign in" when signed out, name initial + menu when signed in. |
| Delete account *(my call)* | Removes Telegram link, addresses, favorites, sessions; keeps orders and the admin Customer record (shop's accounting). Signing in again later creates a fresh account. |
| Admin *(my call)* | Clients list/detail show an "Account (Telegram)" badge and account creation date; no admin editing of accounts. |

### Approaches considered
- **Sign-in:** A) SMS code — rejected by owner for now (paid provider); **B) Telegram bot with contact share + confirm — chosen**; C) email + password — unusual for Uzbek shoppers, no phone proof.
- **Bot link mechanism:** **deep link + contact share (chosen)** — Telegram verifies the phone; Telegram Login Widget — rejected: gives no phone number and needs a domain set in BotFather.
- **Account storage:** **extend Customer (chosen)** — one record per phone already links orders and admin; separate User table — rejected: duplicate identity and phone sync.
- **Bot updates:** **webhook in production + polling script for dev (chosen)**; polling only in production — rejected: needs a long-running worker beside `next start`.

- **Goal:** Shoppers sign in with Telegram and manage their profile, saved addresses, favorites and see all their orders (with details, status and reorder); checkout uses their saved data; they get order-status messages in Telegram.
- **Deliverables:** schema + additive migration; customer auth (login requests, codes, session cookie, rate limits); Telegram webhook + poll script + "Connect bot" in Settings; account pages (overview, orders, order detail, addresses, favorites, profile) + login page; navbar account menu; favorites hearts; checkout integration; status notifications; admin badge; uz/ru/en messages; tests; README.
- **Constraints:** Next.js 16 (read `node_modules/next/dist/docs/` first, AGENTS.md); Prisma 7 + SQLite; next-intl; Tailwind 4; no new runtime dependency except a small QR library if needed (justify, else render QR server-side by an existing dep or omit). Telegram API calls mockable in tests (inject fetch like `telegram.ts`). Additive migration, existing orders/customers preserved. Guest checkout must keep working. Owner: commit only if asked.
- **Non-goals:** SMS/email/password login, social logins other than Telegram, loyalty points, reviews, returns/refund requests, saved payment cards, guest favorites, multiple phones per account, admin editing customer accounts.
- **Assumptions:** the bot token is set in admin Settings; production has HTTPS `SITE_URL` reachable by Telegram; customers have Telegram (others keep guest checkout).
- **Open questions:** none blocking.

## M1 threat model (STRIDE, 2026-11-17 — `agentic-council:threat-model`)
Trust boundaries: browser (untrusted) ↔ Next server (trusted) ↔ SQLite; Telegram servers (semi-trusted, authenticated by webhook secret / bot token) ↔ server; Telegram user (untrusted) ↔ bot.
Flows: F1 start (browser→server: token, browserSecret cookie, checkCode) · F2 Telegram→webhook (/start, contact, callback) · F3 status poll → session cookie · F4 code request/verify · F5 session use on pages/actions · F6 bot→customer notifications · F7 admin "Connect bot".

| STRIDE | Threat | Risk | Mitigation (→ task) |
|---|---|---|---|
| Spoofing | **Phished deep link**: attacker starts sign-in, sends victim the t.me link; victim confirms; attacker's browser (which holds the browser cookie) is signed in as the victim. Browser binding alone does NOT stop this. | **High** | Bot confirm = **choose the code shown on your website screen from 3 buttons** (1 real, 2 random decoys; wrong pick cancels the login) + warning "Only confirm if you are signing in on the website right now; never confirm a link someone sent you" + after every sign-in a **"New sign-in" bot message with "Not me — sign out everywhere"** button (callback `signout_all`). Residual: victim reading the code to the attacker (social engineering) → Medium, accepted. (→ 1.3/1.4 `confirmLogin(token, tgUserId, pickedCode)`, 2.2/2.3) |
| Spoofing | Forwarded/other contact used to claim a phone | High | accept only `contact.user_id === from.id`; phone normalized UZ (→ 1.3, 2.2) |
| Spoofing | Forged webhook updates | High | `x-telegram-bot-api-secret-token` constant-time compare with random 32-byte secret; 401 otherwise (→ 2.2) |
| Spoofing | 6-digit code brute force | Medium | 5 attempts/code, ≤ 3 codes/phone/15 min, ≤ 10 codes/phone/day, ≤ 10 requests/IP/15 min, verify ≤ 20/IP/15 min (→ 1.3) |
| Info disclosure | Code endpoint reveals which phones have accounts | Medium | **uniform response** `{ ok: true }` for linked/unlinked/sent (UI: "If this number is linked to Telegram, a code is on its way"); only `bad_phone`/`rate_limited` differ (→ 3.3, UI 4.1) |
| Info disclosure | IDOR on orders/addresses/favorites | High | every query scoped by session customer id / account phone; 404 on mismatch (→ 3.1 tests) |
| Tampering | Open redirect via `?next=` | Medium | `next` accepted only if it matches `^/(uz|ru|en)(/[^/\\]*)*$` (no `//`, `\`, scheme) (→ 4.1 + test in 3.3) |
| Tampering/CSRF | Cross-site POSTs to account endpoints | Medium | SameSite=Lax + `isSameOrigin` on API POSTs; server actions (Next origin check) (→ 3.3) |
| Elevation | Customer token on admin / staff token as customer | High | `aud: 'customer'` + admin claims check; tests both ways (→ 1.3) |
| Elevation | Phone moves to a new Telegram account (reinstall/new account): old rule "refuse" locks owner out | Medium | Telegram guarantees one account per phone: **newest verified contact wins** — relink, bump `sessionVersion`, notify old chat (→ 1.3 replaces `phone_taken_by_other_telegram`) |
| Repudiation | Disputed sign-ins | Low | keep `CustomerLogin` rows 30 days (cleanup older), "New sign-in" bot message as user-visible trail |
| DoS | Flooding `start` (DB rows) / status polling | Medium | start ≤ 20/IP/10 min + delete logins older than 30 days opportunistically; status ≤ 120/IP/min (→ 3.3) |
| DoS | Notification/code spam to victims' Telegram | Medium | codes only to already-linked chats, per-phone limits above |
| Disclosure | Session theft via XSS | Medium | httpOnly cookie, no token in JS, revocation via `sessionVersion` |

Residual risks (accepted): social-engineered confirmation despite code pick + warning (alert gives recovery); recycled phone numbers (new Telegram owner of an old number sees the previous owner's orders — same as any phone-based login); leaked bot token = full bot takeover (token is full-admin-only in Settings; rotate in BotFather).

## Review focus
1. Someone sends a victim a sign-in link they started → victim must pick the code shown on *their* website screen (they can't know it) and a wrong pick cancels; every sign-in triggers a "New sign-in / Not me" bot message (tests 1.3, 2.2).
2. Contact shared is not the sender's own (forwarded contact) or a non-UZ number → refused with a clear message, no account created (2.2).
3. Brute force on 6-digit codes: 5 wrong attempts kill the code; per-phone and per-IP limits (1.4).
4. Order belonging to another phone, guessed by number → 404 in the account, never data (3.2).
5. Telegram API down / bot blocked by user during status notification or code sending → order status still changes; code request returns a "couldn't reach Telegram" error, not 500 (2.4, 3.4).
